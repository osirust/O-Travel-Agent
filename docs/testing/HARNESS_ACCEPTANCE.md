# Приёмка harness и исходного 106-корпуса

Статус на 25 октября 2026 года: весь исходный корпус прочитан и сопоставлен с текущим кодом; выполнены отдельные детерминированный и stateful-прогоны. Здесь нет утверждения «106 PASS». Подробная передача тестировщику будет подготовлена в конце согласованного этапа.

## Материалы и воспроизводимость

- Источник: [106 исходных сценариев](../research/sources/ostrovok_stress_tests.jsonl), SHA-256 `17b24b8e38fc81a1317213075aa769c6c7c3722a395f648c73fc5e9f4fa2ed2e`. Исходные JSONL/MD/ZIP не редактируются; приоритеты P0/P1 — авторские, не веса жюри.
- [Машинная карта всех 106](../../fixtures/evaluation/corpus-map.json): для каждого `case_id` — общий source SHA, SHA физических байтов записи, исходные реплики/ожидание, typed oracle либо точная причина блокировки, executable check и связанные существующие тесты. `related_existing_test_not_reexecuted` не считается новым PASS.
- [Runner](../../scripts/run_corpus.py) вызывает настоящий domain/inventory и bounded adapters с in-memory MockTransport. Сокетные подключения и DNS заблокированы. БД, секреты, LLM и реальные HTTP не используются. Проверка SHA/полноты карты — preflight, а не тест поведения сценария.
- [Фактический отчёт](../verification/corpus-evaluation-20261025.json) содержит отдельный результат каждого исходного ID, code SHA и ограничения. Исполнение: `python scripts/run_corpus.py` в окружении с зависимостями проекта.
- После последующих изменений domain выполнен [отдельный текущий повтор](../verification/corpus-evaluation-current-20261025.json): те же 57 typed/mock assertions PASS, 49 не исполнялись этим pure-runner. Первоначальный отчёт не перезаписан. Для новых повторов указывать отдельный `--output`, чтобы сохранять историю evidence.
- [Новые русские диалоги](../../fixtures/evaluation/llm-dialogues.json) заморожены **до** модельных результатов: семь cases, пять приёмочных групп, 11 логических model-turns и максимум **12 фактических HTTP-попыток** на серию вместе с fallback. В этом файле результаты не записываются; они должны находиться в отдельном отчёте. Если квоты/модель недоступны, оставшиеся шаги становятся BLOCKED, а не PASS.

## Фактически выполненный объём

Обработаны **106 case IDs**. Для **57** выполнены предметные assertions, все 57 прошли. **49** не исполнялись как поведенческие сценарии: для каждого сохранена явная причина (`NLU_PENDING`, неподдерживаемая возможность, недостаточный oracle или требуемая stateful/UI fixture).

В 57 входят как поддержанные typed-подмножества, так и проверки честного отказа для неподдерживаемого обязательного фильтра. Последние не означают, что исходная возможность реализована. **Реальных NLU-вызовов 0, сетевых HTTP-вызовов 0, полных естественно-языковых case PASS 0.** Долю 57/106 нельзя использовать как качество модели или вероятность победы.

Assertions проверяют реальные результаты, например: календарную ошибку и атомарность state, 3+4 гостиничные ночи и связанный маршрут, возраст ребёнка на разных плечах, точное распределение людей, применение breakfast/refundable на тарифе, целочисленный итог со сборами, сохранение hard constraints, снятие pet-фильтра, stale-plan rejection, единственный подходящий результат, bounded 429/timeout/invalid-JSON ошибки. У каждого негативного inventory-check есть положительный контроль: постоянно пустая выдача не может дать PASS.

Исходные сценарии с хранилищем/HTTP/UI не заменяются in-memory подделкой. Например, BOOK-02 требует конкурентного подтверждения с реальным Store; BOOK-04 — отказа после commit; BOOK-08 — ошибки записи. Связанные автоматические тесты и прежние smoke evidence существуют, но их наличие не выдаётся за повторный case-specific прогон.

### Второй этап: относящиеся stateful fixtures

После исходного отчёта выполнены **10 новых API/PostgreSQL fixtures**, все **10 PASS**. [Тесты](../../tests/test_corpus_harness.py), [JSON evidence](../verification/corpus-harness-20261025.json), [JUnit](../verification/corpus-harness-20261025.xml). Использованы настоящие ASGI-обработчики и PostgreSQL **`otravel_test`**; только интерпретация намерения контролируется StubLLM, а vendor HTTP запрещён NoTravelHTTP. Рабочая `otravel` не использовалась.

Проверены STATE-01; BOOK-01/02/04/08; SOURCE-07; SYSTEM-06/07/08/10. Это stateful typed/controlled-intent части, **не** результаты NLU исходных реплик. В частности:

- Для BOOK-04 ответ теряется на клиентском transport **после успешного server commit**, затем тот же ключ возвращает прежний заказ без дубля.
- Для BOOK-08 ошибка инъецируется в запись завершающего audit-события **внутри транзакции после INSERT order**. API возвращает 503, заказ и версия откатываются; после снятия fault тот же запрос сохраняет ровно один заказ.
- Для STATE-01 три явных single-edit undo возвращают первую версию, затем добавляется refundable. Это не оценка способности модели понять «верни первый вариант».
- Для SYSTEM-08 пересозданы API lifespan/connection pool, но не Docker/Windows и не браузер; состояние, bearer-доступ и идемпотентный заказ сохранились.

Исходный отчёт **57/49 сохранён без изменения**. В сумме **67 различных source IDs** теперь имеют какие-либо исполненные предметные assertions: 34 typed/domain/adapter подмножества, 23 unsupported-boundary guards и 10 stateful подмножеств. **39** остаются без исполнения в этих этапах. Полных естественно-языковых PASS исходного 106-корпуса по-прежнему **0**; отдельная модельная выборка не подменяет эту цифру.

### Третий этап: источник цены/наличия и частичная история

[Дополнительный отчёт](../verification/corpus-remaining-harness-20261025.json) привязывает четыре source IDs к фактически исполненным assertions. Выполнены три сценарных метода и один unit-метод helper: [history JUnit](../verification/corpus-history-20261025.xml), [source-fault JUnit](../verification/corpus-source-faults-20261025.xml). Все четыре метода PASS.

- MONEY-07/BOOK-03 используют **один** относящийся метод `test_new_preview_price_change_stales_previous_active_quote`: авторитетный fake gateway повышает тарифы на 15%, обновляются snapshot/quote, прежнее согласие получает 409, новое принимается. Это производная вариация паттерна MONEY-07, а не проверка буквальных сумм 82 000/91 000 и не live-вызов.
- UX-08: выбранный источник становится недоступным после preview; старый quote stale, orders пусты. По **явному** повторному поиску возвращается другой hotel ID; новая quote и новое согласие создают только имитированный заказ. Автоматический unsolicited re-search и NLU этим не доказаны.
- STATE-09: первый реально показанный hotel A извлекается из долговременного журнала. После hotel B и явно подготовленной typed-транспортной правки на train операция API `replace_hotel` восстанавливает только A. Последние train-legs, люди и бюджет сохраняются; новый DEMO-план проходит совместимость, старый quote отвергается. Транспортная правка подготовлена через проверенный Store commit: публичной операции изменения `Leg.mode` пока нет, и тест не выдаёт setup за языковую способность.

Добавлен read-only [helper истории](../../otravel/history.py): `await plan_history(store, session_id, current_version, limit=2)`. Caller обязан предварительно проверить принадлежность сессии. Helper читает только assistant-run планы этой сессии/поездки, исключает будущие версии и возвращает минимальные проекции `first_saved_plan`/`recent_plans`. Старые суммы отмечены `historical_unverified`, `not_bookable=true`, `consent_reusable=false`; поиск/preview/согласие заново обязательны. Helper не пишет события, не восстанавливает quote и не переносит raw credentials/provider payload в контекст.

Итог по source IDs: **71** имеет исполненные assertions — 34 typed/domain/adapter подмножества, 23 unsupported-boundary guards и **14 stateful подмножеств**. **35** остаются без исполнения в этих этапах. Ни один из этих результатов не является NLU PASS исходных реплик. Исходный отчёт 57/49 сохранён; отдельная модельная серия остаётся отдельным evidence.

Команда повторения stateful-этапа: `python scripts/run_tests.py tests/test_corpus_harness.py -q`. Test helper жёстко выбирает `otravel_test`; файлы source corpus и рабочие данные не удаляются. Все fake model attempts остаются в тестовой БД, без квоты настоящего провайдера.

### Контракт модельного runner

`cases[].initial_trip` — `sample` либо полный TripState. `expect.assertions[].path` — JSON Pointer относительно канонического `GET session.trip`, а не всего HTTP-ответа. `unchanged` сравнивает с каноническим снимком непосредственно после создания этой сессии. Не сравнивать автоматически весь state: версия закономерно растёт, ID сессии назначает Store.

Есть отдельные `session_status`, `waiting_reason`, `no_order_created`, `no_tool_calls`, `no_llm_calls`, `max_questions`. Поддержку каждого дополнительного assertion нужно явно отметить в отчёте runner; неизвестный assertion нельзя молча пропускать как PASS.

При `deferred_while_paused=true` нельзя ожидать completed до resume. `await_buffered_runs=true` означает дождаться обработки ранее принятого run после явного resume; resume сам не требует NLU, но разбор накопленного текста расходует модельную попытку. `setup_actions` и `after_actions` для quote также обязательны для полной приёмки группы. Если runner их пока не поддерживает, соответствующий companion получает NOT_EXECUTED.

## Метрики без завышения результата

1. **Полнота явных изменений:** выполненные ожидаемые изменения / заявленные изменения в реально исполненных turns.
2. **Сохранение:** число неожиданных изменений прежних полей/ограничений. Для обязательных инвариантов целевое число — 0.
3. **Уточнения:** число необходимых вопросов, наличие выдуманных обязательных значений и успешное применение ответа. Не считать длинную анкету одним вопросом только по одному `?`.
4. **Пауза/побочные действия:** фактические model/tool attempts во время pause, неподтверждённые orders, stale acceptance и дубли orders — отдельно; целевое число нарушений 0.
5. **Надёжность и расходы:** фактические HTTP attempts, используемая модель, 429/timeout/schema errors, latency и recovery. Первичная ошибка и успешный fallback не сливаются в «один быстрый успешный вызов».

Знаменатель — только действительно выполненные проверки соответствующего слоя. Отдельно показываются unsupported, blocked, not executed и skipped assertions. Нельзя назвать всю серию успешной, если модельный cap исчерпан после первых диалогов.
