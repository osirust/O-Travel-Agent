# Динамическая география: условия приёмки

27.10.2026. Это будущие содержательные сценарии и обзор архитектурных границ, **не отчёт о реализации или15PASS**. Проверка выполнялась по E-исходникам; Native, API и PostgreSQL не вызывались.

## Что препятствует глобальному охвату

В [domain.py](../../otravel/domain.py) `canonical_city` принимает только локальные aliases/`known_cities()`. [llm_contract.py](../../otravel/llm_contract.py) превращает тот же список в enum: произвольный реальный город нельзя выразить даже корректным ответом модели. В [geography.py](../../otravel/geography.py) страны/города тоже конечны. Добавление Аргентины и ещё одного имени закроет пример, но сохранит этот предел.

[provider_cities.py](../../otravel/provider_cities.py) отделяет запросные идентичности от DEMO, однако остаётся статической парой «имя→страна/поисковое имя» и «имя→IATA». [Store](../../otravel/store.py) сохраняет JSONB поездки/предложений, но не имеет долговечного каталога разрешённых географических идентичностей. RAM-регистрация без сохранённого основания сломает повторную доменную валидацию после рестарта.

Минимальная граница доверия: resolver предлагает кандидатов с `place_id`, страной, регионом и происхождением; harness разрешает неоднозначность; выбранная идентичность и необходимые provider mappings сохраняются. Display name не служит глобальным ключом. Доменная валидация остаётся чистой, без SQL/HTTP; схема конкретной поездки разрешает только подготовленные идентичности/кандидаты. Алиас не создаёт новый город или revision; смена страны/идентичности создаёт новую revision и отзывает старые quotes. Legacy-строки читаются совместимо, без массовой догадки страны.

## 15 необходимых разговоров

Каждый кейс — связный диалог с ответами на фактические вопросы агента. Допустимый новый порядок вопросов требует адаптации следующих коротких ответов, а не ложного FAIL.

| ID | Запрос и продолжение | Обязательный результат |
| --- | --- | --- |
| DG01 | «Хочу в Аргентину, наверное» → «давай» | Сохраняется запрос страны AR; нужен город. Нет автоматического выбора столицы, выдуманного бюджета или сообщения, что страна не существует. |
| DG02 | «Буэнос-Айрес» → «Buenos Aires» → «тот же город» | Русский/латинский варианты связываются с одной подтверждённой идентичностью. Нет второго stay, повторного относительного изменения и отзыва quote только из-за написания. |
| DG03 | «Буенос-Аирес, в Аргентине» → подтверждение кандидата | Исправление опечатки опирается на страну и проверенные кандидаты. Отказ/позднее «да» не подтверждает отменённый кандидат. Цена и доступность из исправления не следуют. |
| DG04 | Одноимённый город; resolver вернул два разных `place_id` | Уточняется страна/регион; первый результат не выбирается автоматически. После выбора provider lookup привязан к выбранному месту, не к одному display name. |
| DG05 | Сербия → «Белгород» → «сохряняем»; отдельно «Белгород, Россия» | Контекстная коррекция предлагает Белград/RS. Явный российский Белгород не переписывается. После принятия canonical/pending/маршрут согласованы; глобальный alias не отравляется. |
| DG06 | «Стамбул в Сербии» → отказ → явный выбор Турции | Известная география Стамбула не меняется из-за пользовательского противоречия. До свежего выбора нет молчаливого переключения; независимые факты группы сохраняются. |
| DG07 | Новый город вместе с origin, детьми, датами и номерами | Неопределённая география не стирает явные независимые факты. Гражданство не выводится из языка/страны назначения. Уточняются только реально отсутствующие или противоречивые данные. |
| DG08 | Неизвестный ранее город отправления → город с несколькими аэропортами | Origin разрешается тем же процессом. Код перелёта подтверждён источником; аэропорт не становится отдельным hotel stay. Не подставляется прежний российский origin. |
| DG09 | Буэнос-Айрес → Стамбул, две семьи/несколько номеров → составная правка | Стабильные traveler/stay/room ID и ограничения сохраняются. Правки адресованы нужному городу. Перелёт/прибытие и hotel dates совместимы; дата отправления не объявляется автоматически датой заезда. |
| DG10 | Место разрешено, но поиск вернул пустую выдачу | Город остаётся настоящим и сохранённым; `NO_MATCHES` не означает «города нет». Нет выдуманной цены, наличия или обязательной замены другим направлением. |
| DG11 | Resolver/поисковый API недоступен → повтор после восстановления | Сохраняются поездка и стадия разрешения; ошибка источника отделена от неоднозначности имени. DEMO вне реального синтетического каталога не создаётся автоматически. |
| DG12 | Сохранить новый город → закрыть процесс → открыть поездку заново | Идентичность/страна/подтверждение и provider binding восстановимы без прежнего RAM-cache. Схема принимает сохранённую поездку; устаревшие цены/согласия не оживают. |
| DG13 | Бюджет RUB/USD, предложение ARS; затем уточнение «доллары» | Исходные суммы/валюты не переписываются. При отсутствии поддержанного FX нет ложного общего итога. AR не означает автоматическую валюту ARS; неоднозначный доллар уточняется. |
| DG14 | Неверная страна/чужой ID/устаревший кандидат в результате resolver или LLM | Такой результат не расширяет allowlist сам собой. Проверяются источник, страна и свежесть выбранного кандидата; чужая сессия не подтверждает выбор. Нужен новый вопрос или безопасная ошибка. |
| DG15 | Подтверждённое новое место → actual поиск → refresh → simulated confirm | Запросы/ответы привязаны к тому же месту, датам и составу. Смена цены/места отзывает quote и требует подтверждения. SANDBOX/indicative не становятся реальной бронью; supplier booking/payment отсутствуют. |

## Что считать доказательством

Для каждого разговора нужны source/package SHA, точные реплики, before/after/pending, raw/checked модельный контракт, provenance разрешения места и provider request/response binding. Проверять содержательные факты, а не только HTTP200, число вызовов или заполненную таблицу. Controlled resolver/Mock/PG подтверждают механизм; actual lookup/search проверяются отдельно. Старые FAIL и ресурсные STOP сохраняются.

Географическая идентичность, поддержка запроса конкретным адаптером, доступ к API и наличие предложения — разные факты. Ограниченный DEMO и текущий FX RUB/USD/EUR не становятся глобальными от расширения resolver. Для старого owner-сценария `no_tools/no_plans` описывает исходную границу701; будущему подтверждённому live-поиску нельзя запрещать доказанные предложения этим историческим условием. Неизвестные наличие/курс/жёсткое свойство остаются неизвестными.
