## PRICE-FRONTEND-DISPLAY-001 — SCREENSHOT_PAYLOAD_UNBOUND

На скриншоте описана карточка Казань → Дубай → Стамбул с суммой `2 808 681 ₽`. Исходный JSON этой карточки и её frontend mapper пока не получены. В локальном checkout нет frontend TSX/JSX и отдельной frontend-ветки; число `2808681` не найдено в имеющихся E-фикстурах и отчётах. R2 относится к маршруту Москва → Белград → Москва и не доказывает происхождение этой карточки.

Пока нельзя утверждать, что frontend показал копейки как рубли. Если **именно JSON карточки** содержит `2808681` в RUB minor units, отображаемое значение — `28 086,81 ₽`. Но это условие ещё нужно проверить на её собственном payload. Само сходство чисел не связывает предложение и скриншот.

В R2 курс ЦБ — `90.0935 RUB/EUR`. Проверенные пары: `15020 EUR minor → 1353204 RUB minor`, то есть `150,20 EUR → 13 532,04 RUB`; `15555 → 1401404`. Контрольный `300,00 EUR` даёт `27 028,05 RUB`. Синтетический `311,75 EUR` даёт **28 086,65 RUB**, а не сумму скриншота. Первое ручное умножение автора этой проверки было ошибочным; два initial FAIL оставлены в `price-media-contract-20261027.xml`. Исправлен expected нового теста, production-код не менялся.

**Условие закрытия:** связать одну карточку с её фактическим `GET /runs/{id}` JSON, валютой и конкретным преобразованием frontend; проверить единицы и групповой охват на этом предложении.

## PRICE-DTO-UNITS-001 — CONTROLLED_PROVIDER_FX_API_PASS

Новый тест проходит цепочку `TravelGateway + httpx.MockTransport → Duffel group total → assemble_plan + CBR reference arithmetic → публичный GET /api/v1/runs/search`. Два взрослых и перелёт с пересадкой не умножают цену группы повторно. Контрольный upstream `total_amount="311.75", total_currency="EUR"` становится:

| Поле | Значение | Смысл |
| --- | --- | --- |
| `offers[].amount_minor / currency` | `31175 / EUR` | Исходная сумма за группу, 311,75 EUR |
| `components[].amount_minor / currency` | `31175 / EUR` | Та же исходная сумма |
| `components[].budget_amount_minor / budget_currency` | `2808665 / RUB` | Справочная оценка 28 086,65 RUB |
| `partial_plan.known_subtotal_minor / currency` | `2808665 / RUB` | Только известный подытог |
| `partial_plan.total_minor` | `null` | Полный итог не подтверждён |

У partial-плана нельзя заменять неизвестный полный итог нулём или выдавать подытог за полную стоимость. У `GROUP_ITINERARY_TOTAL` сумма уже относится ко всей подтверждённой группе. Для DEMO существует legacy `offers[].total_minor`; наличие другого имени поля не меняет единицы. `fx_reference_only=true` не является банковским курсом оплаты.

## MEDIA-PARTIAL-PLAN-001 и MEDIA-HOTEL-IDENTITY-001 — CONTROLLED_PUBLIC_API_PASS

`GET /api/v1/sessions/{id}/media?plan_id=...&state_version=...` допускает сохранённый **partial_plan**, проверяя владельца и версию. `checkout/preview` такой план не находит в готовых планах: фото не превращает его в оформляемую корзину.

Новый API-тест использует настоящий `MediaResolver` и `TravelGateway` с MockTransport: в запросе один точный `hotelId`, в ответе он обязан совпасть. Другой ID при том же названии отеля даёт `PLACEHOLDER`, без чужой фотографии. `media.hotelId` и `sourceHotelId` должны относиться к выбранному supplier-отелю; связывать картинки по названию, стране или первому результату нельзя. Цена и JSON-значения сохранённого плана после media-запроса не изменяются. CDN URL возвращается как ссылка, изображение backend не скачивает.

Actual R2 media-запросов не было. Прежняя авторизованная shape-фикстура `liteapi-hotel-media-lp1b30d1-20261026.json` доказывает только старый захваченный content response, не свежие фото другого отеля.

## MEDIA-RATING-SOURCE-001 — OPEN_PRESENTATION_DATA_GAP

В текущем backend нет типизированного DTO для гостиничных звёзд и отдельного review score. Нормализатор фото их не публикует. Поэтому число `9.2` нельзя превращать в звёзды отеля, а отсутствующую оценку — заменять вымышленными `4.8/5`.

Если оценки нужны карточке, следующий backend-контракт должен отдельно подтвердить supplier hotel ID, `hotel_stars` и `review_score` со шкалой/числом отзывов/источником. До этого отсутствие поля означает отсутствие подтверждённых данных, а не ноль звёзд. Кабинный класс BUSINESS и название авиакомпании на конкретном скриншоте также пока не связаны с исходным ответом поставщика.

## CABIN-CLASS-E2E-001 — OPEN_CHAT_TO_RESPONSE_CONTRACT

Прямой Duffel-адаптер уже принимает `cabin_class=business` и отправляет его в `offer_request`. Но в текущих `SearchPolicy` и схеме `set_search_policy` класса нет; `TripSearch` не переносит его из поездки в запрос каждого плеча. `details.slices` сохраняет ответ поставщика, однако отдельной проверки класса каждого сегмента и каждого пассажира, включая mixed cabin, пока нет. Поэтому запросить business у API технически можно, а обещать исполнение фразы «хочу бизнес-класс» во всей поездке пока нельзя. На этом этапе canonical-схема не расширяется.

Минимальный следующий этап: сохраняемый optional-класс с совместимостью старых JSON → typed/LLM и проверяемый strict transport → передача каждому flight request → доказательство класса из ответа на всех сегментах/пассажирах → та же проверка при refresh → UI-статусы «подтверждён», «смешанный», «неизвестен». `search_request.cabin_class` доказывает запрос, а не полученный тариф. Если бизнес обязателен, экономический или неизвестный сегмент нельзя незаметно принять за полностью бизнес-маршрут. Нужны явное уточнение либо отдельное согласие на mixed cabin.
