# Контракт frontend ↔ backend

Редакция: 27 октября 2026. Источник истины — [otravel/api.py](../otravel/api.py) и выдаваемый им `/openapi.json`; интерактивная схема — `/docs`. Это контракт реализованных HTTP-маршрутов, без экранов, дизайна и продуктового ТЗ. Качество свободного NLU и доступность внешних аккаунтов проверяются отдельно. Карта запуска и файлов — [FRONTEND_HANDOFF.md](FRONTEND_HANDOFF.md), настройки — [API_SETUP.md](API_SETUP.md).

## Дополнения 27 октября

- Ошибки поставщика могут дополнительно содержать `provider`, `upstream_http_status`, `retry_after_seconds`. Основные `code`, `message`, `retryable` сохраняются; дополнительных полей может не быть. HTTP-статус ответа нашего API и статус внешнего источника различаются. Не выводить пользователю raw-объекты или строить логику по тексту сообщения.
- Явный запрос деталей SerpApi через существующий `live/search` возвращает необязательное `run.result.result.live_offers[i].details.supplier_comparison`: продавцы, подходящие комнатные ставки и неизвестные условия. Это `LIVE_INDICATIVE`; детали не запрашиваются автоматически для каждой карточки и не становятся корзиной. [Точный запрос и поля](SUPPLIER_COMPARISON.md).
- У проживания может быть `requested_nights`: число ночей, сохранённое до выбора заезда. При отсутствии поле не выводится. После уточнения заезда backend вычисляет выезд; противоречащая явно заданная дата требует уточнения. Не считать дни и ночи одинаковыми.
- Типизированная смена транспорта: `POST S/commands` с `{"type":"set_leg_mode","target_id":"<owned-leg-id>","value":{"mode":"train"}}`; второй режим — `flight`. Сохраняются ID, города, даты и другие части поездки. Наличие реального поезда этой операцией не подтверждается.
- В `pending_question.field` возможны `stay.requested_nights` и `leg.mode`. Вопросы и пояснения для пользователя брать из `text`; технические ID показывать через собственные названия остановок/участков.
- Пауза и уточнение независимы: при `waiting_reason="user_pause"` может сохраняться `pending_question`. Не очищать его в клиенте. Дополнения остаются в очереди до явного resume; после него backend возвращает сохранённый вопрос. Preview/новое подтверждение во время паузы возвращают409 `user_paused`.
- LiteAPI refresh использует выбранный `offerId` через sandbox prebook, без создания брони и оплаты. Новая цена и условия попадают в новый quote; источник остаётсяSANDBOX. Точный ответ Google Flights «нет результатов» означает `NO_MATCHES`, а не сбой всего сервиса.

## Адрес и авторизация

Базовый адрес переносимого Docker Compose-запуска: `http://localhost:8080`; внешний порт меняется через `APP_PORT` в собственном `.env`. Другой origin frontend должен быть явно внесён сервером в `CORS_ORIGINS` через запятую; wildcard автоматически не включается. Собственный PostgreSQL поднимается Compose, отдельная установка БД или WSL-скрипты владельца не требуются.

Текущий стенд владельца `http://localhost:8084` имеет отдельный профиль: OpenRouter `dots-studio/dots-3-note-preview:free`, HYBRID, LiteAPI Sandbox, Duffel test и подтверждённый SerpApi Free. Это не переносимые настройки по умолчанию и не адрес удалённого сервера для другого компьютера. Его актуальные настройки видны в `/api/v1/providers/status`; наличие ключа в статусе не подтверждает квоту или успешный поиск. Переносимый запуск начинает с DEMO-политики и личных ключей в репозитории не содержит.

Схема и очищенные примеры ответов для интеграции: [frontend/openapi.json](frontend/openapi.json), [frontend/api-examples.json](frontend/api-examples.json). Примеры синтетические, не активные предложения и не действующие токены.

Создать сессию:

```http
POST /api/v1/sessions
Content-Type: application/json

{}
```

Ответ `201` содержит `session_id`, `trip_id`, `state_version`, `trip_version` (его alias), `status`, `trip`, `waiting_reason`, `pending_question`, `available_actions` и **`session_token`**. Токен возвращается один раз. В запросе допустим необязательный `initial_trip`, соответствующий `TripState` из OpenAPI; поля черновика могут отсутствовать. Сервер назначает собственные trip/session ID и начальную версию.

Все перечисленные ниже ресурсы сессии и run требуют:

```http
Authorization: Bearer <session_token>
```

Токен одной сессии не даёт доступа к другой. Hash владельца и внутренний input run в HTTP-ответы не попадают. Не передавать токен в URL и не передавать ключи LLM/туристических API из браузера: они настраиваются на сервере. Для утраченного токена отдельного endpoint восстановления сейчас нет.

Публичны создание сессии, `/`, `/health`, `/api/v1/providers/status`, `/docs`, `/redoc` и `/openapi.json`. OpenAPI содержит схему `SessionBearer` для защищённых маршрутов.

## Маршруты

В таблице `S = /api/v1/sessions/{session_id}`.

| Метод и путь | Назначение |
|---|---|
| `GET S` | Актуальный snapshot: `trip`, `state_version`, статус, вопрос/пауза. |
| `GET S/messages` | `{messages:[...]}`: последовательность `sequence`, `role`, `text`, идентификаторы и время. Служебный ввод формы показан как структурированная команда, без внутреннего префикса. |
| `GET S/events?after=0` | JSON-журнал и `next_cursor`; формат ниже. |
| `GET /api/v1/runs/{run_id}` | Статус и сохранённый результат конкретной обработки; требуется токен её сессии. |
| `POST S/messages` | Принять текст, вернуть `run_id`. |
| `POST S/commands` | Структурированные изменения без NLU. |
| `POST S/control` | Pause/resume; отдельно undo последней правки и cancel текущей обработки. |
| `POST S/demo` | Явно заменить черновик сложным DEMO-примером и выполнить DEMO-поиск. |
| `POST S/search` | Поиск целой поездки по сохранённой `search_policy`: DEMO или HYBRID. Необязательный `mode` проверяет совпадение с политикой; несоответствие409 не запускает поиск. |
| `POST S/live/search` | Запросить отдельные внешние компоненты/погоду; их source labels обязательны. |
| `POST S/checkout/preview` | Перепроверить компоненты сохранённого DEMO/смешанного плана и создать корзину для имитации оформления. |
| `POST S/checkout/confirm` | Явно подтвердить конкретные версии; создать один локальный тестовый заказ. |
| `GET S/orders` | `{orders:[...]}` — тестовые заказы этой сессии. |
| `GET /health` | SQL readiness PostgreSQL; это не проверка LLM или live-цен. |
| `GET /api/v1/providers/status` | Redacted-конфигурация провайдеров; `configured` не означает успешный live-прогон. |

## Приём команды и polling результата

```http
POST S/messages

{
  "client_message_id": "<new-client-uuid>",
  "text": "Добавь ребёнка шести лет и перенеси возвращение на два дня",
  "expected_version": 1
}
```

`expected_version` у текста необязателен; при наличии проверяется во время durable intake. Ответ `202`:

```json
{
  "session_id": "<session-id>",
  "run_id": "<run-id>",
  "status": "pending",
  "duplicate": false,
  "poll_url": "/api/v1/runs/<run-id>"
}
```

`202` означает принятую команду, а не готовую поездку. Сохранять client UUID до известного результата. При сетевом повторе отправлять **тот же UUID, текст/операции и expected_version**. Сервер вернёт прежний run с `duplicate=true`; тот же ключ с другими параметрами даёт `409`.

Опрос `GET /api/v1/runs/{run_id}` можно начинать с интервала 0,5–1 секунды. Run-статусы: `pending`, `running`; конечные — `completed`, `failed`, `conflict`, `interrupted`, `cancelled`. При локальном тайм-ауте интерфейса сначала перечитать существующий run, не создавать автоматически новую операцию с новым UUID.

Форма результата сейчас содержит сохранённую оболочку Store:

```json
{
  "run_id": "<run-id>",
  "session_id": "<session-id>",
  "status": "completed",
  "based_version": 1,
  "llm": {"provider": "openrouter", "model": "<actual-model-id>", "latency_ms": 123},
  "result": {
    "state_version": 2,
    "state": {},
    "reply": "<assistant text>",
    "changes": [],
    "error": null,
    "result": {"plans": [], "questions": [], "warnings": [], "source_type": "DEMO", "llm": {}}
  },
  "error": null
}
```

Это сокращённый пример формы, не готовый фактический ответ. Полезные пути:

| Путь в ответе `GET /api/v1/runs/{run_id}` | Значение |
|---|---|
| `run.result.reply` | Готовый текст ответа. Сервер может сформировать его по каноническому состоянию; это не обязательно исходная реплика LLM. |
| `run.result.changes` | Проверенные изменения before/after. |
| `run.result.result.plans` | Планы целой поездки; не путать с отдельными внешними компонентами. |
| `run.result.result.live_offers` | Отдельные результаты `/live/search`. |
| `run.result.result.weather` | Ответ погодного адаптера. |
| `run.result.result.search_explanation` | Необязательные `{text,summary}` с источниками и причинами отклонения компонентов HYBRID-поиска. |
| `run.llm`, `run.result.result.llm` | Фактические provider/model/попытки, когда был вызов модели. |

`assistant_message` внутри сохранённой оболочки — объект сообщения, поэтому для строки использовать `reply`. `search_explanation.text` уже добавлен сервером к `reply`; повторно склеивать их не нужно. В `summary` есть `source_counts`, типизированные `reasons`, канонические подписи направлений и `omitted_reason_count`. Поле может отсутствовать; отдельного alias `source_explanation` API не выдаёт. Отсутствие подтверждённой вместимости в этом объяснении не означает, что номера распроданы. После окончания run получить `GET S` и заменить snapshot по его версии.

Статусы сессии: `NEW`, `TRIP_DRAFT`, `WAITING_USER`, `OPTIONS_READY`, `RECOVERABLE_ERROR`, `BOOKED_DEMO`. Текущее выполнение отслеживать по run, не выдумывать session-статус `SEARCHING`, которого API сейчас не устанавливает.

Ответ без новых операций и вопросов (`control:none`) не запускает поиск. В результате может быть `no_changes:true`; существующие варианты, версия и текущий вопрос сохраняются. Не очищать карточки из-за отсутствия нового `plans` в таком run. Реальная правка, явный запрос поиска или продолжение работы могут запустить пересборку; один общий `control.continue` у справочного ответа этого не доказывает. `conflicts` блокируют весь предложенный batch; вопросы `unknowns` допускают сохранение только непротиворечивых изменений.

## События: JSON polling; SSE пока отсутствует

```http
GET S/events?after=120
Authorization: Bearer <session_token>
```

```json
{
  "events": [
    {
      "sequence": 121,
      "event_id": "<event-id>",
      "session_id": "<session-id>",
      "run_id": "<run-id>",
      "event_type": "MODEL_RESPONSE_RECEIVED",
      "state_version": 1,
      "payload": {"provider": "openrouter", "model": "<actual-model-id>", "latency_ms": 123},
      "created_at": "<ISO timestamp>"
    }
  ],
  "next_cursor": 121
}
```

Запрашиваются события с `sequence > after`; последовательность может иметь пропуски. При reconnect использовать последний `next_cursor`, а не требовать непрерывные номера. Дедупликация по `event_id`/`sequence`. События показывают прогресс; `GET S` остаётся snapshot для UI. Событие старой версии не должно перезаписывать новую поездку.

**SSE endpoint и `text/event-stream` в текущем backend не реализованы.** `/events` возвращает `application/json`, в том числе при произвольном Accept. Формат SSE `id/event/data` не утверждён и не должен имитироваться frontend. Сейчас использовать polling с Bearer-заголовком. После `RUN_FAILED` или окончания одного run не прекращать возможность дальнейшего session polling и получения новых событий.

## Ожидание вопроса и явная пауза

- `WAITING_USER + waiting_reason="clarification"`: `pending_question` содержит `question_id`, `text`, список `questions`, `state_version`, `reason`. Показывается первый существенный вопрос; одна реплика может заполнить сразу несколько полей.
- `WAITING_USER + waiting_reason="user_pause"`: работа остановлена; новые дополнения долговременно принимаются как pending runs, но не передаются LLM до явного продолжения. `pending_question` не должен превращаться в форму подтверждения покупки.
- Явный control: `POST S/control {"action":"pause"}` либо `{"action":"resume"}`. Возвращается свежий session snapshot. Control изменяет версию и инвалидирует старые корзины.
- Без LLM распознаются только точные управляющие фразы: `подожди`, `пауза`, `подожди, я ещё дополню`/`допишу` и варианты `еще`; для продолжения — `продолжай`/`продолжить` (регистр и завершающие `.!` несущественны). **«Не продолжай» не возобновляет работу.** Для остальных формулировок нужна LLM либо control-кнопка.
- Поздний результат не возобновляет паузу и не заменяет актуальное состояние. Дополнения, принятые до более позднего явного resume, не должны повторно включать старую паузу.

Выбор карточки, ответ «да» на вопрос и согласие на конкретную корзину — разные действия. Чат сам по себе не создаёт заказ: создание идёт через `/checkout/confirm`.

## Формы без LLM: типизированные команды

```http
POST S/commands

{
  "client_message_id": "<new-client-uuid>",
  "expected_version": 1,
  "operations": [
    {"type":"set_budget","value":{"amount_minor":78000000,"currency":"RUB","scope":"whole_trip"}},
    {"type":"shift_return","value":{"days":2}}
  ],
  "search": true
}
```

`expected_version` здесь обязателен. Весь batch атомарен: при недопустимой операции часть полей не сохраняется. Ответ — `202/run_id`, затем тот же polling. Между формой и обработкой доменное состояние могло измениться: `stale_state` означает перечитать поездку и проверить изменения перед новым запросом. Pause/resume сами по себе не должны терять очередь корректных форм.

Обычные типы правок: `set_origin`, `set_budget`, `add_traveler`, `remove_traveler`, `update_traveler`, `upsert_stay`, `remove_stay`, `set_constraint`, `clear_constraint`, `shift_return`, `replace_hotel`, `set_search_policy`. Отдельно поддерживается `undo` по правилам ниже. Адресные операции используют `target_id` из snapshot; изменяемые поля — в `value`. Примеры:

```json
[
  {"type":"set_origin","value":{"city":"Казань"}},
  {"type":"add_traveler","value":{"id":"child-new","type":"child","age":6,"group_id":"family-1"}},
  {"type":"update_traveler","target_id":"child-new","value":{"age":7}},
  {"type":"set_constraint","value":{"key":"refundable","value":true,"hard":true}},
  {"type":"replace_hotel","target_id":"stay-antalya","value":{"hotel_id":"<hotel-id-from-saved-offer>"}}
]
```

Не подавать их автоматически: существование адресных ID и необходимость изменения проверяются по актуальному snapshot. `replace_hotel` принимает именно `hotel_id`, а preview — `plan_id`. Не генерировать эти значения из номера карточки. Неизвестные операции отклоняются. Противоречивые записи одного поля в одном batch не применяются по принципу «последний победил»: требуется уточнение.

Деньги — целые `amount_minor`/`total_minor` вместе с `currency`, для RUB это копейки; float и bool вместо суммы недопустимы. DEMO сейчас проверяет общий бюджет `whole_trip` в RUB. Тип `Budget.currency=str` и возможность сохранить поле командой не означают сквозной поддержки переключения валют. Готовые RUB/USD/EUR-переключатель и FX-конвертация ещё не реализованы. Валюты поставщика сохраняются; несовместимая с бюджетом цена отклоняется, без выдуманного курса. `shift_return` продлевает/сокращает последнюю остановку, сохраняя остальные. Rooms принадлежат конкретному stay, их `traveler_ids` ссылаются на устойчивые ID людей. Полную форму `TripState` брать из OpenAPI, не из текста чата.

Предварительные guards реализации: 10 путешественников, 4 остановки, 5 номеров **на остановку**. Они обозначены как proposed, не как утверждённые владельцем продуктовые пределы. Неизвестные даты/возраст/город требуют уточнения; подходящих комбинаций или бюджета может действительно не оказаться.

## Undo и отмена обработки — разные действия

Отменить последнюю успешную доменную правку:

```http
POST S/commands

{
  "client_message_id":"<new-undo-uuid>",
  "expected_version":2,
  "operations":[{"type":"undo","value":{}}],
  "search":false
}
```

Undo — единственная операция batch, без `target_id` и дополнительных полей; `search:true` для него не допускается. Альтернатива — `POST S/control` с `{"action":"undo","client_message_id":"<new-undo-uuid>","expected_version":2}`. Обе формы возвращают `202/run_id`; ключ и версия обязательны.

Результат записывается **новой, большей ревизией**, содержит `result.result.undo` с `undone_revision`/`restored_from_revision` и before/after в `changes`. Последовательные новые undo отменяют более ранние ещё не отменённые правки; они не переключают состояния туда-обратно. Поиск без доменных изменений, неуспешный batch, pause/resume и создание заказа не считаются правкой, которую undo отменяет. При отсутствии истории — `nothing_to_undo`, без изменения доменных полей и версии.

Цены, планы, старые quote/consent и состояние оформления не восстанавливаются. После undo нужен отдельный поиск, новый preview и новое согласие. Даже если значения снова совпадают с прежними, старый plan/quote не становится актуальным по новой версии. Уже созданные тестовые заказы остаются неизменными. Undo на явной пользовательской паузе остаётся в очереди до resume, как остальные типизированные правки.

Остановить **текущую обработку**, не откатывая успешные правки:

```http
POST S/control

{"action":"cancel","client_message_id":"<new-cancel-uuid>","expected_version":2}
```

Ответ `202/run_id` относится к команде отмены; её результат содержит `cancelled_run_id` либо `null`, если отменять уже нечего. Исходный активный run (или старейший pending до команды отмены) получает терминальный статус `cancelled`. Поздний ответ не применяется. Поездка, история и заказы не удаляются. Это не новая пауза: после отмены можно отправлять другой запрос. Уже существующая явная пауза сохраняется.

Повтор отмены/undo с тем же client UUID, версией и параметрами возвращает прежний run. Другие параметры при том же UUID — `409`; stale version не разрешает отменять неожиданную новую обработку. Отмена без активного/подходящего pending run не увеличивает версию. Когда отмена действительно прервала обработку, новая версия инвалидирует текущие quote.

Без модели также поддерживаются точные `отмени обработку`, `отмени текущий поиск`, `останови поиск`. Неоднозначное «отмена» не приравнивается к удалению поездки или отмене заказа. Модель может предложить `undo` как одиночную операцию или `control.cancel`; эти решения всё равно проходят серверные guards.

## Явный DEMO-путь

1. Создать сессию и сохранить её token.
2. `POST S/demo {}` → дождаться run. Это намеренная замена черновика примером, не автоматический fallback незнакомого текста.
3. `GET S` → актуальная версия; планы взять из run.
4. Изменять через `/commands`, при необходимости `search:true` либо отдельный `POST S/search {"mode":"DEMO"}`.
5. Выбрать сохранённый план и пройти preview/confirm.

`/demo` и `/search` принимают необязательные `client_message_id`, `expected_version`, `mode`. `/demo` загружает именно DEMO-поездку. Для `/search` `mode`, если передан, должен совпадать с сохранённой политикой (`DEMO` или `HYBRID`); для DEMO-примера выше это `"DEMO"`. При автоматическом UUID от сервера сетевой повтор может стать новой поисковой командой; для контролируемого replay лучше задавать UUID клиентом.

Пример — Казань → Стамбул (3 ночи) → Анталья (4 ночи) → Казань; 6 взрослых, 3 ребёнка, 2 семьи, 3 номера на остановке. Identity сессии сохраняется. Все гостиницы, маршруты, тарифы и наличие здесь вымышлены. `plans[].room_assignments` содержит размещение на каждой остановке; у offer есть `kind`, `component_id`, `hotel_id` для проживания, `total_minor`, `currency`, подробный `breakdown` и source labels. `changes[]` содержит `field`, `before`, `after`, `operation`, `target_id`.

## Внешний поиск и происхождение данных

```http
POST S/live/search

{
  "client_message_id":"<new-client-uuid>",
  "kind":"hotels",
  "provider":"liteapi",
  "request":{
    "hotelIds":["<known-provider-hotel-id>"],
    "checkin":"2026-11-06",
    "checkout":"2026-11-09",
    "occupancies":[{"adults":2,"children":[6]}],
    "guestNationality":"RU",
    "currency":"RUB"
  },
  "demo_fallback":false
}
```

Это пример формы, не проверенный реальный hotel ID. `kind`: `hotels`, `flights`, `weather`. Реализованы адаптеры hotels `liteapi`/`serpapi`, flights `duffel`/`serpapi`; для weather передавать `provider:"open_meteo"` и `request:{city,latitude,longitude}`. Flight request зависит от выбранного провайдера: IATA `slices`, даты, полный состав пассажиров; точные условия — [API_SETUP.md](API_SETUP.md) и схемы адаптера. Ключи и произвольные HTTP URL в request запрещены.

Маршрут называется `live/search`, но фактический статус определяется данными, а не именем URL:

| Source label | Как отображать |
|---|---|
| `DEMO`, `price_kind="synthetic"` | Вымышленная цена и наличие; локальный тестовый сценарий. |
| `SANDBOX` | Тестовая среда поставщика; не реальная рыночная цена или бронь. |
| `LIVE_INDICATIVE` | Поисковые/ориентировочные сведения, без обещания доступности и bookability. |
| `NO_MATCHES` | Поставщик вернул пустую выдачу; это не доказательство невозможности поездки. |

Показывать источник, валюту, охват цены и время получения, если они есть; не складывать nightly и total как равнозначные суммы. Ответы `/live/search` — отдельные `live_offers`/weather, **не готовая проверенная многогородская корзина**.

Поиск всей поездки выполняется через `/search` по `trip.search_policy`: `mode:"HYBRID"`, выбранные `hotel_provider`/`flight_provider`, `guest_nationality` для LiteAPI и явный `demo_fallback`. Сборщик связывает компоненты с остановками, номерами, участниками и версией. Проверенный смешанный путь включает два проживания SANDBOX и маркированные DEMO-компоненты транспорта; это не полностью live/bookable-поездка. В каждом плане читать `components`, `coverage`, `room_assignments`, `blockers` и `ready_for_simulated_checkout`, если они присутствуют. Флаг `ready_for_real_booking` текущая сборка не подтверждает.

Фото загружаются отдельным owner-auth `GET S/media?plan_id=<id>&state_version=<version>`. Ответ привязан к сессии, текущей версии и сохранённому плану; медиа не входит в стоимость/offer hash. Полный DTO, ограничения и обработка отсутствующих фото: [HOTEL_MEDIA.md](HOTEL_MEDIA.md). Не добавлять `photos` в экономический снимок.

При `demo_fallback:false` ошибка поставщика сохраняется в failed run, состояние поездки остаётся. При явно заданном `true` доступна маркированная DEMO-замена с `provider_error`; она не превращается в реальные данные.

## Preview, подтверждение и версии

```http
POST S/checkout/preview

{"plan_id":"<plan-id-from-this-session>","state_version":2}
```

План должен быть сохранён в run **этой сессии**, соответствовать текущей версии и пройти проверки. Preview поддерживает DEMO и смешанные планы, перепроверяя внешние компоненты через адаптеры. Indicative/sandbox-компоненты не становятся настоящим бронированием. Ответ содержит `quote_id`, `quote_version`, `state_version`, `expires_at`, `status`, `plan`.

```http
POST S/checkout/confirm

{
  "quote_id":"<quote-id>",
  "quote_version":1,
  "state_version":2,
  "idempotency_key":"<new-operation-uuid>",
  "confirmed":true
}
```

`confirmed` — только JSON boolean `true`, не строка. Подтверждать показанные пользователю quote/версию/сумму. Изменение поездки, pause/resume или истечение quote требует нового preview и нового осознанного подтверждения. После `409` нельзя автоматически подтверждать новую сумму.

Повтор **той же операции** с тем же ключом и теми же параметрами возвращает прежний заказ. Тот же ключ с другим содержимым — `409`; разные ключи не дают создать второй заказ по тому же quote. Сохранить UUID до известного исхода; при сетевой неопределённости прочитать `/orders`, не создавать другую оплату.

Заказ содержит `order_id`, `is_demo:true`, `booking_created_at_supplier:false`, `status:"BOOKED_DEMO"`. Реальная оплата и бронь у поставщика не создаются. Версия сессии после заказа меняется; перечитать `GET S`.

## Модель, резерв и ошибки

### Дополнения состояния после проверки 80 диалогов

`trip.route_policy.kind` принимает `round_trip`, `one_way`, `open_jaw`, `undecided`; у `open_jaw` есть `end_city`. Конечный город рейса не создаёт проживание. Неопределённый конец требует уточнения до оформления.

Примеры операций для существующих ID поездки:

```json
[
  {"type":"set_route_policy","value":{"kind":"open_jaw","end_city":"Москва"}},
  {"type":"clear_preference","value":{"key":"departure_time"}},
  {"type":"upsert_group","target_id":"family-1","value":{"traveler_ids":["adult-1","child-1"],"keep_separate":true}},
  {"type":"set_constraint","value":{"key":"breakfast","value":true,"hard":true,"stay_id":"stay-1","room_id":"room-2"}},
  {"type":"set_constraint","value":{"key":"nonstop","value":true,"hard":true}}
]
```

`upsert_group` задаёт полный состав одной группы и синхронизирует `traveler.group_id`. Не угадывать принадлежность участников к семье. `room_id` у условия требует `stay_id`; сейчас это условия завтрака/возвратности тарифа. Для `nonstop` адрес проживания/номера не используется; отмена — `clear_constraint` с этим ключом. `nonstop=false` разрешает пересадки и не требует рейс с пересадкой.

Новые адресные вопросы: `search.guest_nationality`, `route.kind`, `route.end_city`, `group.membership`, `party.removal`. Гражданство не выводится из языка или направления. Состояние неизвестных семей сохраняется; пользователь выбирает фактический состав.

Session default-параметры сервера `DEFAULT_SEARCH_MODE`, `DEFAULT_HOTEL_PROVIDER`, `DEFAULT_FLIGHT_PROVIDER` действуют только при отсутствии явно заданного `initial_trip.search_policy`. Переносимый запуск сохраняет DEMO по умолчанию (hotel LiteAPI / flight SerpApi); текущий профиль владельца 8084 использует HYBRID (hotel LiteAPI / flight Duffel). Уже сохранённая политика поездки не меняется от появления ключей в конфигурации.

`processing_in_progress`, `clarification_required`, `trip_requires_recovery` запрещают новую корзину/оформление до завершения обработки или уточнения. Не повторять подтверждение новой цены автоматически. Точный идемпотентный повтор ранее созданного заказа по-прежнему возвращает тот же заказ.

`run.result.result.response_source="contextual_slot"` означает ответ на сохранённый адресный вопрос без нового вызова модели. Не показывать прежнюю модель/её попытки как источник этого ответа. Источник `llm` включает extraction и последующие серверные guards; это не необработанная реплика модели.

`response_source="canonical_saved_answer"` — ответ по сохранённым бюджету, датам, маршруту или конкретному показанному плану без вызова модели и нового поиска. Использовать обычный `run.result.reply`; прежнюю модель не показывать как источник этого ответа. Версия поездки, текущий вопрос и существующий quote сохраняются. `plans_preserved=true` обозначает прежнюю выдачу своей сессии и текущей версии, без обновления цены или наличия. При неоднозначном номере план не выбирается автоматически. Этот ограниченный путь не заменяет обработку смешанных команд и свободного диалога.

`response_source="readonly_answer"` — один вызов модели для выбора разделов ответа, затем канонический текст из состояния и показанных предложений. Отображать `reply`, а не внутренний ответ модели с кодами разделов. Этот путь не меняет поездку, вопрос или quote и не выполняет новый поиск. Фактический provider/model находится в обычном `llm`; `response_role=readonly_answer_v1` описывает роль вызова.

Новые необязательные extraction metadata `speech_act=CHANGE|ASK|PROPOSE`, `information_subject` отделяют справочный вопрос и предложение от команды изменить поездку. В результате `conversation` содержит тип и справочный объект, `candidate_operations` — только неисполненные предложения для аудита. Frontend не отправляет их автоматически в commands/checkout. Справочный ответ не начинает обязательную анкету и не меняет ранее выбранное направление.

Курируемый известный город может сохраняться в TripState отдельно от покрытия поиска. Белград, Белгород и Тбилиси не добавляют предложения в семигородный DEMO-каталог. Для текущего направления приоритетен канонический маршрут; metadata нового подтверждённого города обновляется. Предпочтения `price_priority=lowest_total` и `departure_time=early_morning` не задают численный бюджет, точное время или гарантию глобально минимальной цены.

После успешной LLM-обработки фактическая модель видна в `GET run.llm` и `run.result.result.llm`: `provider`, `model`, `latency_ms`, `attempts`. Показывать это значение, а не жёсткую подпись «Gemma»: явно настроенная бесплатная резервная модель может ответить вместо primary. Failed run может содержать известные попытки в `error.llm`; при отсутствии самого вызова metadata может быть `null`.

Резерв по умолчанию не выбирается. Явный `OPENROUTER_BACKUP_MODEL` допустим только как отличающийся `:free` ID с настроенным ключом. Разрешённое переключение OpenRouter учитывает подтверждённый upstream shared-pool 429, сеть/timeout, 5xx или невалидную схему.401/402/403, account/key/workspace/credit и429 неизвестного происхождения резервом не обходятся. Gemini/OpenRouter допускают до 2 попыток на run; Groq, Cloudflare и Z.ai — одну, без автоматического fallback. Readonly-ответ ограничен одним вызовом.

Дневные пределы приложения: `MAX_LLM_CALLS_PER_DAY` по умолчанию40; для Z.ai явно настраивается до2000. У Cloudflare отдельный `MAX_CLOUDFLARE_LLM_CALLS_PER_DAY`, default40, максимум2000. Это внутренние ограничения, а не остаток vendor-квоты. Классифицированная CF3036 означает исчерпанную суточную бесплатную квоту; неизвестный429 может дать инженерное ожидание, не обещание времени сброса поставщика. UI не должен добавлять собственные автоматические повторы. Ответ Z.ai1113 в текущих проверках говорит о ресурсах конкретного аккаунта, а не о постоянной недоступности провайдера.

В `llm.usage` и `llm.attempts[].usage` могут присутствовать vendor-reported `input_tokens`, `output_tokens`, `total_tokens`. Неизвестный расход не равен нулю. Если были несколько попыток, верхний `usage` описывает ответившую модель; расходы неудачных попыток доступны отдельно. `request_metrics` содержит байты и SHA, а не оценку токенов. Cloudflare neurons не равны числу сообщений или токенов.

### Дата до выбора остановки

В новой версии после «выезд 14 ноября» при нескольких остановках backend сохраняет абсолютную дату и задаёт адресный вопрос. `pending_question.field` равен `stay.check_in` либо `stay.check_out`, `target_id=null`, `context.target_selection_required=true`. В `context.date_proposal` есть `resolved_date`, `candidate_stay_ids` и `based_state_version`; это серверный пакет, его нельзя редактировать или отправлять обратно как доверенную команду.

Frontend может показать варианты из текущего `trip.stays` и отправить обычный ответ с городом, порядковым номером или ID выбранной остановки. Backend проверит адресность, версию и даты. После успешного изменения пакет удаляется атомарно; неоднозначность или конфликт оставляют поездку без этой правки. Составной ответ «вторая и уменьши бюджет» пока вызывает уточнение без изменений.

Это контракт текущей ветки. Исторические прогоны на85160ef не описывают нынешний стенд8084. При развёртывании новой версии сверяют schema/source manifest; код, профиль и квоты текущего прогона фиксируются в его отдельном отчёте.

### Ответы о сохранённой поездке

Вопросы без правок сохраняют текущие варианты и не обязаны запускать новый поиск, даже если модель вернула общий `continue`. Вежливый явный запрос поиска выполняется отдельно. Правка вместе с вопросом сохраняет обе части: например, возраст меняется, затем ответ показывает состав из обновлённого состояния.

`result.conversational_response` может содержать `kinds` и `facts_source="canonical_state_and_shown_plans"`. Это признак формирования ответа по сохранённым фактам, а не ещё один вызов модели. Не выводить внутренние traveler/stay IDs пользователю.

Для просмотра актуального варианта может вернуться:

```json
{"suggested_action":{"type":"preview_cart","plan_id":"<current-plan-id>","state_version":7}}
```

Это предложение предварительного просмотра, не quote и не заказ. Frontend использует существующий `POST S/checkout/preview` с авторизацией и текущей версией. При неоднозначном выборе, отрицании, гипотезе, чужом или устаревшем плане действие не предлагается. Подтверждение покупки из этого поля выводить нельзя.

Источник LLM и источник туристических данных показывать отдельно: API-модель может работать с DEMO-каталогом. Наличие ответа LLM не подтверждает актуальность цен или доступ к реальному поставщику.

Без ключа LLM работают формы, control, явный DEMO и ограниченные канонические ответы о сохранённой поездке. Для произвольного свободного NLU нужен доступный LLM API; при отказе модели нет имитации успешного разбора, состояние сохраняется. Детерминированный пример и управляемые тестовые ответы адаптера не являются общим NLU PASS.

Ошибки HTTP имеют форму:

```json
{"error":{"code":"stale_state","message":"Состояние поездки изменилось.","retryable":false}}
```

Основные статусы: `401/403` — token/access; `404` — отсутствующий ресурс этой сессии; `409` — версия/идемпотентность/устаревшая корзина; `413` — слишком большой ввод; `422` — схема/доменный запрос; `503` — недоступное хранилище/синхронный провайдер. Ошибка фонового LLM/tool обычно приходит через failed run после исходного `202`, а не как HTTP 503 на уже принятый POST. Не показывать пользователю raw traceback, секреты, raw HTTP-заголовки или ключи.
