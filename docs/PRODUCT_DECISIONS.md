# Продуктовые решения O!Travel Agent

Актуальная редакция по ответам владельца от 24 октября 2026 года. Это зафиксированные требования и границы будущего ТЗ. Владелец поручил запомнить решения и ждать следующих указаний; реализация не начата.

## Цель продукта

Агент самостоятельно доводит сложный запрос до совместимой поездки и тестового оформления. Главный приоритет — корректность полного сценария, сохранение пожеланий и понятное объяснение результата.

**DEC-004 — главная особенность:** интеллектуальная пересборка всей поездки со сравнением «Было → Стало». Пример изменения: «Добавь ребёнка, замени второй отель, сократи бюджет на 20 тысяч и перенеси возвращение на два дня».

Агент должен пересчитать затронутые отели, номера, транспорт, стоимость и условия, проверить ограничения и сохранить остальные пожелания. Для каждого существенного изменения требуется объяснение. Это требование, а не описание реализованного поведения.

## Данные и резервная работа

**DEC-003, редакция 2 — гибридная система с приоритетом реальных данных.** Основной режим использует реальные API для поиска отелей, транспорта, тарифов и доступности. Перед тестовым оформлением обязательна повторная проверка цены и наличия.

Параллельно нужен качественный синтетический каталог для сложных сценариев, тестирования и продуктового деморежима. При недоступности поискового API агент сохраняет состояние поездки и переключается на деморежим с явным обозначением тестовых данных. Работоспособность проекта не должна целиком зависеть от внешних сервисов.

Это заменяет прежнее ограничение «синтетика только для тестовых фикстур». Живые, сохранённые и демонстрационные предложения должны оставаться различимыми. Демопересчёт не подтверждает реальную цену или наличие; имитированное оформление не создаёт бронь у поставщика.

**DEC-001, редакция 2 — отказ LLM.** Основная модель работает через API. Если сама LLM недоступна, сохраняется поездка и доступны формы и готовые демосценарии. Полноценный свободный диалог без внешней LLM не требуется. UI должен явно показывать ограниченный режим и причину перехода.

Точную границу перехода при частичном отказе источников — вся поездка или отдельные компоненты — нужно описать в ТЗ. Пользовательские ограничения сохраняются; прежние цены и подтверждения нельзя автоматически объявлять актуальными после смены источника или состава плана.

## География и сложные поездки

**DEC-002, редакция 2 — ограниченная география с поддержкой сложных маршрутов.**

- Россия: Москва, Санкт-Петербург, Сочи, Казань.
- Зарубежные направления: Стамбул, Анталья, Дубай.
- Опорный сложный маршрут: Казань → Стамбул → Анталья → Казань.

В первой версии нужны несколько городов и отелей, несколько номеров, взрослые и дети с различными требованиями участников группы. Географию расширяем по мере подключения API; охват всего мира не обещается. Архитектура не должна жёстко привязывать обработку поездки к одному сценарию.

Максимумы остановок, номеров, путешественников и допустимое время пересборки пока не установлены. Семь направлений задают географию, но не численные пределы одного запроса.

## Обязательные возможности

- Распределение сложной группы по нескольким номерам.
- Проверка бюджета, вместимости, дат и совместимости маршрутов.
- Пересборка затронутых компонентов с сохранением остальных требований.
- Сравнение реальных тарифов разных поставщиков.
- Сохранение состояния при ошибках LLM и поисковых API.
- Явно обозначенный резервный деморежим.
- Финальная проверка цены и доступности перед тестовым бронированием.

**DEC-005 — источники сравнения.** Допустим один агрегатор, если в его данных различимы реальные поставщики. Два независимых поисковых API не являются обязательным условием. Нужно отдельно подтвердить, что выбранный агрегатор предоставляет необходимые сведения; разные вымышленные подписи не считаются разными реальными поставщиками.

## Команда

В команде три человека, включая владельца.

- **Глеб:** fullstack; по сообщению владельца, больше работал с frontend. Его логично рассматривать как кандидата на ведение интерфейса, но окончательное назначение ещё не зафиксировано.
- **Женя:** зона ответственности, доступное время и объём участия ещё не согласованы.
- **Владелец:** зона ответственности и доступное время ещё не зафиксированы.

До подтверждения загрузки нельзя рассчитывать план как три полных параллельных потока. Предварительные участки для обсуждения: интерфейс и UX; harness, состояние и проверки; API, данные и упаковка. Каждый автор проверяет свою часть, интеграция и перекрёстная проверка остаются общими. Это предложение по организации, а не назначение задач.

## Что остаётся определить перед ТЗ

1. Провайдер LLM, поисковый агрегатор, разрешённые доступы, лимиты расходов и доступ проверяющих. По последнему подтверждению владельца, поисковых доступов пока нет.
2. Численные пределы сложной поездки и допустимое время ответа/пересборки.
3. Поведение при частичном отказе: правила смешанного плана, маркировка источников, возврат из demo в live и необходимость обновления ранее выбранных предложений.
4. Условия сопоставимости тарифов и доступность реальных supplier ID/названий у агрегатора.
5. Конкретные роли и время участников; интерфейсные детали согласовываются с Глебом.

Ни один из этих пунктов не является разрешением создавать аккаунты, расходовать квоты или начинать реализацию. Следующее действие — дождаться отдельной команды владельца.
