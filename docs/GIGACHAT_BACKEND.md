# GigaChat: Compose и отдельный локальный стенд

GigaChat подключается явно через `LLM_PROVIDER=gigachat`. Модель стенда — `GigaChat-3-Ultra`, личный scope — `GIGACHAT_API_PERS`. Ключ, подтверждение доступного Freemium-пакета и фактический остаток токенов относятся к аккаунту владельца. Приложение не включает billing и не переключается на платную модель.

Authorization Key вводится скрыто командой `py scripts/configure_gigachat.py`. Ключи и `.env` не передаются в Git или архиве для проверяющих.

## Docker Compose

В локальном `.env` задаются `GIGACHAT_AUTH_KEY`, `GIGACHAT_MODEL=GigaChat-3-Ultra` и, после проверки своего бесплатного пакета, `GIGACHAT_FREEMIUM_CONFIRMED=true`. Поле `LLM_PROVIDER` выбирает провайдера. По умолчанию пример конфигурации сохраняет OpenRouter и не разрешает вызовы GigaChat.

`GIGACHAT_CA_FILE` в примере оставлен пустым. Compose подставляет `/app/certs/gigachat-root-ca.pem`: Dockerfile копирует проверенный публичный сертификат именно туда с правами `0444`. Это путь **внутри контейнера**. Путь Windows или Native WSL в этом поле внутри контейнера работать не будет без отдельного согласованного монтирования.

`MAX_GIGACHAT_LLM_CALLS_PER_DAY=40` — защитный лимит приложения, не квота сервиса и не число доступных токенов. Settings принимает целое значение от 0 до 1000. Наличие ключа или поднятого контейнера не доказывает доступность модели.

## Отдельный Native-стенд владельца

Контроллер `scripts/gigachat_backend.py` использует только:

- source `/home/aegml/projects/otravel-gigachat-20261027` в C-backed WSL `AegML-Hackathon`;
- свою БД `otravel_gigachat_eval` в проверенном контейнере `otravel-db-1`;
- loopback-порт `8085`, отдельные process identity и private log;
- выбранные поля из `/home/aegml/projects/otravel/.env`. Файл `.env` внутри нового source не читается.

Перед запуском root-актор устанавливает проверенный committed archive. В выбранной Master-конфигурации Native-путь сертификата должен быть:

```dotenv
GIGACHAT_CA_FILE=/home/aegml/projects/otravel-gigachat-20261027/certs/gigachat-root-ca.pem
```

Этот публичный файл должен существовать, читаться пользователем `aegml`, быть обычным файлом без symlink и без записи для группы/остальных. Не используйте `/app/certs/...` для Native или закрытый root-only runtime-каталог. Сертификат применяется только к TLS-клиенту GigaChat; проверка имени сервера и сертификата остаётся включённой. Системное хранилище доверия не меняется.

Посмотреть план без чтения ключей и изменения среды:

```powershell
py scripts/gigachat_backend.py --action plan
```

После проверки source, CA и готовности провайдера root-актор запускает `--action start`. Контроллер откажется занимать чужой порт, усыновлять неизвестную существующую БД или возобновлять pending-запуски. Новая БД создаётся только в своём фиксированном scope; HBA дополняется точными `/32`-правилами для этой БД и роли. Другие БД, PostgreSQL Windows и стенд `8084` не меняются. Удаления или пересоздания БД нет.

При успешном startup адрес чата — `http://localhost:8085/debug`; подтверждение запуска сохраняется в `docs/verification/gigachat-backend-20261027.json`. Команды `--action status` и `--action stop` адресуют только зарегистрированный процесс этого стенда.

Startup проверяет импорт, PostgreSQL, health и локальный status провайдеров, но не вызывает OAuth, список моделей или генерацию. Поэтому `RUNNING` ещё не подтверждает действительность ключа, внешнюю TLS-связность, баланс или качество ответов. Эти проверки и отдельный диалог выполняются после запуска и записываются отдельно. В частности, установка CA сама по себе не устраняет сетевой/TLS timeout.
