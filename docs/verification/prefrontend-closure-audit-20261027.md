## Что проверить перед новым actual checkpoint

1. **HARNESS-004-DEMO-COMMAND-IGNORED-001:** exact initial фразы PF-DURATION-03/01, PF-GROUP-04/01, PF-SOURCE-07/01 должны выбирать DEMO и не запускать live tools. Затем довести PF-GROUP-04 до реальной составной правки и ответа «Было→Стало»; сейчас эта часть NOT_REACHED.
2. **H004-GEO-LATE-FIELD-TYPO-001 / H004-GEO-UNCONFIRMED-CITY-LOSS-001:** E исправлен и424controlled PASS сохранены, но нужен тот же связный remote-model повтор. Удалять exact city из oracle ради PASS нельзя.
3. **HARNESS-004-ORDER-REPLY-SUPPRESSED-001:** exact actual T10 сохранён в [regression fixture](../../fixtures/regression/order-reply-cf-r2-20261027.json). После ownPG DEMO-order канонический ответ обязан назвать существующий тестовый заказ и отсутствие supplier booking; mixed edit/cancel/hypothesis не должны поглощаться новым prehook. Peer нашёл именно «Есть ли заказ? Я отменяю текущий поиск.» и «Есть ли заказ? Теперь вылетаем из Казани.» как перехваченные ранней версией hook. Root добавил узкий словарь полного status-вопроса; read-only повтор8pure примеров отвергает эти mixed/conditional реплики и сохраняет два обычных status-вопроса. Новые PG-проверки и actual квалификацию ведёт root.
4. **Новая общая квалификация:**3914PASS относится к checkpoint до последних E-repairs. Новые targeted PASS должны войти в новый общий результат, затем exact commit/package/deploy и ограниченный actual повтор. Native ab378 нельзя считать проверкой ещё не развёрнутого E-кода.
5. **Ресурсные границы:** CF r2 закончен на последнем ходе HTTP429; state сохранён, дата сброса неизвестна. Не добавлять автоматически retry, новый платный профиль или локальный Qwen. Без доступного сильного API remote acceptance остаётся открытой, даже если cached/PG проверки проходят.

Nightly hotel cap: жёсткий лимит за ночь не реализован отдельным фильтром; канонический честный capability reply и сохранение whole-trip бюджета проверены8PG/0fail/0skip (`.local/evaluation/after80-20261026/capability-faq-20261027-pg.xml`). Это следует закрывать только как bounded unsupported-capability ответ, а не как поддержку такого фильтра или проверку всех новых формулировок.

## R3: исправление oracle без сокрытия дефекта

Новая версия подготовлена отдельным файлом [prefrontend-dialogues-20261027-r3.json](../../fixtures/evaluation/prefrontend-dialogues-20261027-r3.json), SHA `c24251b6900c8d3650181bd0c7f038c801f537e67b3aab5c0005feea5f54e2b5`. R1/R2 и их результаты остаются неизменны; r3 пока не исполнен.

- **PF-GEO-01/07:** требовать точный `pending_question.context.requested_destination={kind:city,name:Белград,country_code:RS}` и `trip.stays=[]`. Неподдержанный город хранится как запрос, без выдуманного bookable stay. На старом actual ab378 это продолжает давать FAIL: там после отказа осталась только страна Сербия. Старый canonical stay predicate был неверен, но потеря выбранного city — настоящий отдельный дефект.
- **PF-GEO-01/12 и PF-PAUSE-08/02:** сравнить все semantic trip поля, исключив только state_version; отдельно проверить revisiondelta=1 и user_pause. Возрасты/города/даты/сумма/пожелания не исключаются. Остальные readonly/no-op проверки всего trip должны оставаться строгими.
- Остальные тексты/actions/requires/business checks не меняются. Слабые source FAQ assertions в r2 не доказывают содержательный ответ; усиление ответов источников нужно добавлять как отдельные новые predicates с положительными и отрицательными примерами. Для текущего CF source06 вручную подтверждены2DEMO/2SANDBOX и отсутствие реальной брони, а post-order T10 FAIL сохранён.
- R3 требует поддержать два узких новых оператора в client runner, протестировать semantic delta и запрет иных изменений, зафиксировать новый driver SHA. Наличие JSON/patch само по себе не является запущенной проверкой.
