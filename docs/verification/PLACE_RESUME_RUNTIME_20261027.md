# Сохранённое продолжение выбора места

Новый `resume_place` создаётся сервером в той же транзакции, где явное
возобновление меняет control revision и переносит проверенный deferred packet.
Он выполняется после принятых во время паузы дополнений, переживает повторное
открытие Store и не вызывает LLM. Текущие version, scope, candidate IDs и TTL
проверяются перед продолжением. Повторный или заменённый marker не выполняет
старое действие. SQL-транзакция не удерживается во время HTTP.

Проверено 68 относящимися тестами, включая 19 новых pure/PG/ASGI проверок.
Кнопка и текст «продолжай» проверены с контролируемыми адаптерами; настоящих
LLM и туристических HTTP-вызовов не было. Это не полная квалификация recovery.
Подробности и SHA: [place-durable-resume-20261027.json](place-durable-resume-20261027.json).

## HARNESS-004-PLAINTEXT-CONTROL-CRASH-OPEN — CLOSED_AFTER_CONTROL_COMMIT_SCOPE

**Исходный триггер:** принято текстовое «продолжай»; `Store.set_control` уже завершил
транзакцию и сохранил continuation, но процесс остановился до отдельного
`Store.finish_run` для самого текстового control run. Последний может остаться
pending. Существующий recovery через `_drain/_process` не распознаёт этот
текст как уже применённый control и может передать его в NLU.

**Исправлено:** `Store.set_control(control_run_id=...)` проверяет принятую
точную реплику и принадлежность run, затем в одной транзакции сохраняет control,
его завершённый ответ и continuation. Harness больше не завершает этот run
отдельным `finish_run`. Повтор завершённого control возвращает прежний результат
до создания новой revision или continuation. Очередь продолжения сохраняет своё
отдельное правило актуальности; старые согласие и котировка не восстанавливаются.

**Доказательство:** первоначальные 2 PG-теста упали на оставшемся pending run.
После исправления 8 PG/ASGI-проверок прошли: инъекция `BaseException` сразу после
SQL commit, новая app/Store lifetime, обычный worker только своей сессии, 0 NLU,
1 контролируемый geocoder-вызов, сохранённый бюджет и отсутствие повторных control
и revision при replay. Ошибка внутри транзакции отдельно откатывает все записи.
Проверены чужой run, неверная реплика, старая версия и завершение собственного
active lease. Это контролируемая инъекция, не остановка PostgreSQL или OS kill.
[Точная квитанция](control-message-atomicity-20261027.json).

## HARNESS-004-ACCEPTED-CONTROL-PRECOMMIT-001 — CLOSED_BOUNDED_RECOVERY_SCOPE

**Исходный триггер:** `intake_message` уже принял текстовое «продолжай», но процесс
остановился до commit первого control-транзакции, когда сессия ещё на паузе.
Обычные `_drain/claim_run` не запускают pending run при `user_pause`, а повтор
того же client ID сам по себе не переисполняет control.

**Исправлено:** bounded recovery проверяет user-message и серверное событие
принятия, точную исходную команду и владельца. До ordinary pause barrier он
может завершить только подтверждённый control; обычные сообщения остаются на
паузе. Событийные sequence задают порядок: более новая принятая команда или
подтверждённая кнопка превращает старый control в terminal superseded/no-op.
Два worker используют те же session/run locks и не создают вторую revision.

**Доказательство:** первоначальный PG RED оставлял принятый resume pending.
Итоговый набор — 90 related PASS / 0 skip: 12 новых precommit PG, 2 pure
task-interleaving, 8 aftercommit и 68 предыдущих связанных проверок. Это один
относящийся набор, не новый общий прогон приложения.
[Квитанция](control-precommit-recovery-20261027.json).

## HARNESS-004-PAUSE-TASK-EPOCH-001 — CLOSED_CONTROLLED_INTERLEAVING_SCOPE

Peer-проверка нашла ещё одну гонку: задержанный ответ старой pause мог отменить
task, созданный уже после более нового resume. Оба исходных pure-теста упали.
Теперь direct/recovery hooks перед отменой перечитывают session и требуют
тот же exact version и `user_pause`; между выбором task и `cancel` нет await.
Оба сценария входят в итоговые 90 PASS. Произвольные распределённые сбои,
exactly-once внешнего HTTP, OS kill и потеря диска этим не квалифицированы.
