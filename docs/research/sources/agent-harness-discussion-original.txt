# Архитектура AI Agent Harness для «О!дин запрос» — план до 29 октября

Я предлагаю строить не обычного чат-бота, а полноценный Agent Harness с долговременным состоянием в PostgreSQL, контролируемыми инструментами, системой уточнений, обработкой ошибок и автоматической проверкой результатов.

Один участник уже занимается дизайном и frontend. Поэтому этот план — для разработчика агентной логики, backend и базы данных.

### Самые важные принципы

1. PostgreSQL — источник истины. История сообщений, изменения требований, обращения к LLM, вызовы инструментов, ошибки, версии маршрутов и заказы сохраняются в базе.
2. LLM понимает и предлагает действия, Python проверяет и исполняет. Нейросеть не управляет PostgreSQL напрямую и не может самостоятельно подтвердить покупку.
3. Агент умеет остановиться и ждать. Если данных недостаточно, он сохраняет вопрос и текущее состояние. Следующее сообщение продолжает тот же процесс.
4. Незнакомые запросы обрабатываются универсальной логикой. Никаких маршрутов, зашитых под конкретные тестовые фразы.
5. API поставщиков необязательны для работоспособности. Сейчас используем универсальные mock-инструменты, позднее подменяем их реальными адаптерами.

Это соответствует ключевым требованиям Островка: уточнять только необходимое, подбирать и пересобирать поездку, объяснять решения и доходить до имитации покупки. На защите агенту дадут заранее неизвестные запросы.&#x20;

Важное уточнение: PostgreSQL — не посредник передачи HTTP-запросов к LLM и поставщикам. Все внешние обращения делает backend, но регистрирует их начало, завершение, результат и ошибку в PostgreSQL. Так получится полная история исполнения без необходимости давать нейросети прямой доступ к SQL.

Именно эта архитектура позволит посмотреть, почему агент задал вопрос, изменил маршрут, отклонил предложение или не смог завершить поиск.

## 3. PostgreSQL: что именно сохранять

Я бы не ограничивался хранением истории переписки. Это позволит восстановить чат, но не понять, почему агент принял определённое решение.

Нужны следующие таблицы:

| Таблица           | Назначение                                           |
| ----------------- | ---------------------------------------------------- |
| `sessions`        | Сессия, текущий этап, версия состояния поездки       |
| `messages`        | Все пользовательские и ответные сообщения            |
| `agent_runs`      | Каждый запуск обработки нового сообщения             |
| `agent_events`    | Все важные решения и переходы между этапами          |
| `llm_calls`       | Запросы к модели, ответы, ошибки, токены, задержки   |
| `tool_calls`      | Аргументы вызова инструмента, результат, ошибка      |
| `state_revisions` | История изменений поездки и возможность отката       |
| `offers`          | Предложения от демо- или реальных поставщиков        |
| `quotes`          | Пересчитанные версии корзины                         |
| `demo_orders`     | Подтверждённые тестовые бронирования                 |
| `geo_cities`      | Города, страны, координаты и альтернативные названия |

Для динамического состояния удобно использовать `JSONB` с отдельными колонками для идентификаторов, версий и статусов. PostgreSQL поддерживает запросы и индексацию JSONB.&#x20;

### Пример: что будет записано при одном запросе

Пользователь пишет:

> «Давай вместо Сочи в Стамбул, но бюджет не увеличивай, и добавь ребёнка 6 лет».

Пример журнала Agent Harness

1. USER_MESSAGE_RECEIVED

   Сообщение и ID сессии сохранены
2. INTENT_EXTRACTED

   MODIFY_TRIP, изменение направления и гостей
3. STATE_PATCH_PROPOSED

   Сочи → Стамбул, добавить ребёнка 6 лет, бюджет сохранить
4. STATE_UPDATED

   Новая версия поездки; предыдущая доступна для отката
5. OFFERS_INVALIDATED

   Прежние отели, транспорт и корзина больше неактуальны
6. SEARCH_STARTED / SEARCH_COMPLETED

   Новый поиск через универсальные инструменты
7. CONSTRAINTS_CHECKED

   Бюджет, вместимость и остальные условия проверены
8. ASSISTANT_RESPONSE_SAVED

   Итог, объяснения, карточки и новое состояние UI

Если API упал после пятого события, мы знаем, какой шаг не завершился. Подтверждённое состояние не пропадает.

Но важно не держать транзакцию PostgreSQL открытой, пока LLM отвечает или пользователь думает над вопросом. Для конкурентных изменений используем версию состояния и проверку перед записью. Для коротких критических операций можно использовать блокировки строк PostgreSQL.&#x20;

## 4. Адаптивность: как научить агента разбирать любые новые сообщения

Вместо огромного системного промпта и сотен `if` я предлагаю использовать единый структурированный язык изменений поездки.

LLM не должна полностью переписывать состояние после каждого сообщения. Она возвращает только изменения.

Например:

```
{
  "intent": "modify_trip",
  "operations": [
    {
      "op": "set",
      "field": "destination",
      "value": "Стамбул"
    },
    {
      "op": "add",
      "field": "children_ages",
      "value": 6
    }
  ],
  "preserve": ["budget"],
  "requires_clarification": false
}
```

Затем Pydantic проверяет структуру, а `State Manager` проверяет, допустимы ли такие изменения и какие предложения надо пересчитать.

Использование Structured Outputs помогает получать ответы определённой JSON-структуры, но не гарантирует, что смысл извлечён верно. Поэтому после LLM всё равно нужны программные проверки, особенно конфликтов и обязательных требований.&#x20;

### Какие типы сообщений агент должен понимать

| Тип сообщения        | Пример                         | Действие                                  |
| -------------------- | ------------------------------ | ----------------------------------------- |
| Идея                 | «Куда-нибудь к морю»           | Предложить направления                    |
| Готовый запрос       | «Казань, 5 ночей, двое»        | Начать подбор                             |
| Дополнение           | «И ещё с собакой»              | Добавить новое условие                    |
| Исправление          | «Нет, ребёнку 7, а не 6»       | Исправить возраст                         |
| Удаление             | «Собака не едет»               | Удалить условие                           |
| Замена               | «Лучше Стамбул»                | Поменять направление                      |
| Уточнение            | «Я имел в виду общий бюджет»   | Изменить тип бюджета                      |
| Сравнение            | «Почему второй лучше?»         | Объяснить различия                        |
| Откат                | «Верни предыдущий вариант»     | Восстановить ревизию                      |
| Ссылка               | «Беру тот первый»              | Найти ранее показанный вариант            |
| Конфликт             | «7 ночей, но всего 4 дня»      | Задать уточнение                          |
| Неизвестный параметр | «Нас трое, один ребёнок»       | Уточнить возраст                          |
| Пауза                | «Подожди, ещё дополню»         | Сохраниться и ждать                       |
| Неизвестный город    | «Хочу в X»                     | Проверить название или уточнить           |
| Покупка              | «Всё, оформляй»                | Проверить корзину и получить согласие     |
| Нестандартный вопрос | «А если сильно задержат рейс?» | Проанализировать риск                     |
| Ошибка сервиса       | API вернул 429                 | Сохранить ход и корректно обработать сбой |

Один входной текст может содержать сразу несколько намерений. Например, одновременно поменять даты, убрать животное, добавить ребёнка и спросить, сколько удалось сэкономить.

Поэтому важна обработка нескольких операций в одном сообщении, а не распознавание только одного намерения.

## 5. Самый важный модуль — Question Engine

Это я бы выделил в самостоятельную часть backend.

Он должен различать информацию, без которой нельзя действовать, и сведения, которые пока необязательны.

Например:

Пользователь

«Хочу в ноябре к морю с ребёнком, тысяч за 100».

Агент определяет

Ноябрь

Море

Ребёнок

\~100 000 ₽

Город выезда неизвестен

Возраст неизвестен

Уместный ответ агента

«Могу предложить несколько направлений для отдыха у моря. Из какого города планируете выезд? Это поможет оценить дорогу и уложиться в бюджет».

Агент уже может обсуждать направления, но не должен утверждать, что нашёл полную подходящую поездку за 100 тысяч без данных о выезде и составе гостей.

### Правила уточнений

- Спрашивать только о параметрах, блокирующих текущий этап.
- По возможности задавать один содержательный вопрос за ход.
- Не спрашивать повторно о том, что уже известно.
- Если пользователь дал ответ сразу на несколько вопросов, извлечь всё.
- Не путать отсутствие данных с отрицательным ответом.
- Сохранять сам вопрос и ожидаемые поля в PostgreSQL.
- После ответа продолжать с сохранённого состояния, а не перезапускать всю беседу.

Если пользователь пишет «Подожди, я сейчас добавлю ещё условия», harness устанавливает `WAITING_USER`, сохраняет всё необходимое и прекращает обработку. Следующее сообщение продолжает поездку с этой версии.

После ошибки модели должен действовать тот же принцип: новая попытка не начинает пустой диалог.

## 6. Как сделать, чтобы агент работал не только на примерах

Это самая сложная часть без внешних туристических API.

Нужно разделить универсальность понимания запросов и доступность фактических предложений. Первую можно реализовать с LLM и структурированным состоянием. Вторую без источников данных гарантировать нельзя.

Поэтому я предлагаю универсальный Mock Travel Engine.

Любой пользовательский запрос

Географический справочник

Города, страны, альтернативные названия, часовые пояса

Генератор воспроизводимых демо-предложений

Даты, гости, номера, тарифы, условия, транспорт

Проверка ограничений и ранжирование

Объяснимые варианты или корректный отказ

В качестве географической основы можно использовать офлайн-выгрузку [GeoNames](https://download.geonames.org/export/dump/readme.txt?utm_source=chatgpt.com). У неё есть справочник десятков тысяч городов, координаты, часовые пояса и альтернативные названия. Данные распространяются по CC BY 4.0 с требованием атрибуции.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://download.geonames.org\&sz=32)

download.geonames.org



Для демонстрационных предложений используем стабильные идентификаторы и детерминированную генерацию:

- Для одного города, периода и тарифа предложения воспроизводимы.
- Увеличение числа гостей влияет на размещение и стоимость.
- Завтрак и гибкая отмена влияют на подходящие тарифы.
- Изменение дат пересчитывает затронутые части маршрута.
- Для нескольких городов создаются отдельные этапы поездки.
- Если вариантов нет, система сообщает об этом, а не снимает обязательные ограничения.

При этом придуманные отели и рейсы всегда помечаются как демо. На неизвестный город агент может ответить вопросом, предложить общую структуру путешествия либо честно указать отсутствие проверяемых данных.

Это даст универсальный механизм для произвольных формулировок и широкого набора направлений, а не систему, умеющую только повторять несколько подготовленных историй.

## 7. Подключение реальных API в последние два дня

Самое важное — подготовить адаптеры уже сейчас.

```
class TravelProvider:    async def search_hotels(self, request): ...    async def search_transport(self, request): ...    async def search_transfers(self, request): ...    async def reprice(self, quote): ...
```

Сегодня методы реализует `MockProvider`. Позднее — `LiveProvider`.

Agent Harness не должен знать, из какого API пришли предложения. Он получает одинаковую структуру данных и сведения об источнике.

| Период        | Режим                                                 |
| ------------- | ----------------------------------------------------- |
| 25–26 октября | Mock-поиск, LLM, память, пересборка, корзина          |
| 27 октября    | Первые реальные интеграции, если есть доступы         |
| 28 октября    | Проверка реальных цен, отказов и переключения на mock |
| 29 октября    | Сдача стабильной версии                               |

Я бы не откладывал подключение самой LLM на последние два дня. LLM API и туристические API — разные зависимости. Для неизвестных естественно-языковых запросов языковая модель нужна уже на этапе разработки агента.

Если ключа LLM пока нет, можно подготовить тестовые структурированные ответы для проверки state machine и ограниченный rule-based fallback. Но такой режим не гарантирует понимание произвольной речи.

## 8. Контракт для участника, который делает интерфейс

Чтобы участник frontend не зависел от реализации агента, ему нужно передать единый API уже 25 октября.

| Endpoint                                              | Назначение                   |
| ----------------------------------------------------- | ---------------------------- |
| `POST /api/v1/sessions`                               | Создать разговор             |
| `POST /api/v1/sessions/{id}/messages`                 | Отправить сообщение          |
| `GET /api/v1/sessions/{id}`                           | Получить состояние поездки   |
| `GET /api/v1/sessions/{id}/messages`                  | Получить историю             |
| `GET /api/v1/sessions/{id}/events`                    | Получить прогресс агента     |
| `POST /api/v1/sessions/{id}/offers/{offer_id}/select` | Выбрать предложение          |
| `POST /api/v1/sessions/{id}/checkout/preview`         | Пересчитать корзину          |
| `POST /api/v1/sessions/{id}/checkout/confirm`         | Подтвердить тестовую покупку |

Каждый ответ должен содержать структурированные поля: `status`, `assistant_message`, `trip`, `offers`, `cart`, `pending_question`, `changes`, `warnings`, `data_mode`.

Тогда frontend сможет показывать карточки, прогресс, пересборку и корзину без анализа произвольного текста ассистента.

## 9. Проверка адаптивности и устойчивости

Не надо пытаться вручную предусмотреть каждую возможную фразу. Надо проверять универсальные свойства агента.

Я бы обязательно прогнал такие цепочки:

Тест 1. Уточнение и продолжение

«Хочу на море» → агент спрашивает город → «Из Казани, нас четверо, двое детей 4 и 10 лет» → агент извлекает все данные сразу и продолжает.

Тест 2. Просьба подождать

«Хочу в Дубай» → «Подожди, ещё допишу» → приложение перезапускается → «Нас трое, 7 ночей, до 150 тысяч» → состояние восстановлено.

Тест 3. Сложная пересборка

«Стамбул 3 ночи, Анталья 4 ночи, три номера» → «Во втором городе поменяй отель, один номер убери, но даты не трогай» → пересчитываются только необходимые компоненты.

Тест 4. Ошибка LLM/API

Модель отвечает с ошибкой → состояние сохраняется → пользователь повторяет запрос → старые требования и выбранные варианты не исчезают.

Тест 5. Изменение во время оформления

Пользователь подтвердил вариант, потом добавил ребёнка → прежняя корзина становится недействительной → агент рассчитывает новую и снова запрашивает согласие.

Для этого нужен отдельный Test Harness. Он должен сравнивать не буквальные ответы модели, а результаты: правильно ли изменились данные, какой вопрос задан, сохранились ли ограничения, не создано ли два заказа.

Для каждого прогона сохраняем в PostgreSQL время обработки, тип запроса, количество уточнений, ошибки инструментов, затраты LLM и итоговый статус.

### Что я считаю главным условием успеха

Не количество агентов, не огромная база данных и не самый дорогой LLM.

Самое ценное — агент, который понимает новое сообщение как изменение реальной задачи, помнит уже согласованные параметры, спрашивает только необходимое, умеет останавливаться, продолжать после ошибок и самостоятельно проверяет результат своих действий.

Если именно это будет работать, а frontend красиво показывать происходящее, у вас получится сильный продуктовый прототип, а не просто демонстрация языковой модели.
